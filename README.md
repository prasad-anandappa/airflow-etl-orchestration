# airflow-etl-orchestration

[![CI](https://github.com/prasad-anandappa/airflow-etl-orchestration/actions/workflows/ci.yml/badge.svg)](https://github.com/prasad-anandappa/airflow-etl-orchestration/actions/workflows/ci.yml)

Production-style ETL orchestration on Apache Airflow 2.10 — not a tutorial
DAG. Five DAGs demonstrating the patterns that separate a demo from a
platform: **dynamic DAG generation from config**, a **deferrable sensor**,
a **data-quality gate with failure routing**, an **explicit backfill
strategy**, and **SLA + failure alerting hooks** — with the whole thing
guarded by DagBag integrity tests in CI.

## The DAGs

| DAG | Source | Pattern |
|---|---|---|
| `etl_payments`, `etl_refunds`, `etl_customers` | generated by `dags/dag_factory.py` from `dags/pipeline_config.yml` | one graph, N feeds; adding a pipeline is a YAML diff |
| `payments_daily_taskflow` | hand-written, TaskFlow API | flagship feed: contract validation → quality gate → transform → idempotent load |
| `backfill_payments` | hand-written, trigger-only | bounded date-range replay via dynamic task mapping |

Every pipeline runs the same graph — **sense → gate → load → verify** —
because the graph is a platform invariant; only the file, table, keys and
checks vary.

## Run it

```bash
docker compose up airflow-init      # migrations + admin user (one-time)
docker compose up -d                # webserver :8080, scheduler, triggerer
mkdir -p data/landing data/quarantine
cp data/sample_payments.csv "data/landing/payments_$(date -F).csv"
# unpause payments_daily_taskflow in the UI (admin/admin) and watch it run

# tests (no Docker needed — a plain venv):
pip install -r requirements.txt
python -m pytest                    # DagBag integrity + logic unit tests
```

## Design decisions & trade-offs

**Dynamic generation vs copy-pasted DAGs.** Three near-identical feeds as
three files would drift: a gate fix would land in one and not its siblings.
The factory keeps the graph in exactly one function; per-feed variance is
data (YAML). The known cost of generation is opacity — a config typo
becomes a parse-time failure — so config is validated eagerly in the
factory and CI asserts every expected `dag_id` exists with zero import
errors. The hand-written TaskFlow DAG stays hand-written deliberately: the
flagship feed has steps (contract validation, a transform) that don't
generalise, and forcing them into the factory would contort both.

**Deferrable sensing.** The extract arrives "some time in the morning."
A poke-mode FileSensor would hold a worker slot for the whole wait;
reschedule mode frees the slot but churns task instances. The custom
`DeferrableFileSensorOperator` hands the wait to the triggerer
(`FileAvailableTrigger`) — no worker slot, no task slot — and resumes when
the file lands. Trade-off stated plainly: you must run a triggerer, and
resume latency is seconds. For sub-minute waits, poke is fine; for
unbounded upstream windows, deferrable is the only sane default.

**The quality gate routes failures; it doesn't just fail.** On a failed
check, `DataQualityGateOperator` moves the extract to quarantine (never
deletes — operators need evidence), writes a per-check JSON report next to
it, and *then* fails the task into the alerting hooks. A gate that only
logs is a dashboard.

**Backfill strategy: catchup off, replay explicit.** All daily DAGs use
`catchup=False`. History is replayed only through `backfill_payments` with
a bounded conf (`{"start": ..., "end": ...}`, 92-day safety cap), one
mapped task per date, parallelism capped, and — because loads are
idempotent per logical date with content-hash verification — the entire
backfill is safely re-runnable. "Turn on catchup and hope" is how a
scheduler outage turns into an uncontrolled replay storm against a
warehouse; this repo encodes the opposite posture.

**Idempotent loads.** `common/loaders.py` keys each load by
(table, logical_date) in a ledger with a content hash: same data → verified
no-op; same date, *different* data → hard error instead of silent
overwrite. Retries, backfills and corrected re-deliveries all flow through
this one discipline.

**Alerting that can't take the pipeline down.** Failure and SLA-miss
callbacks write a machine-readable incident file and best-effort POST to a
webhook; a dead webhook is logged, never raised — an alerting bug must not
become a pipeline outage.

**Versioning.** Factory + config are versioned together in git; generated
DAG ids are stable (`etl_<name>`), so renaming a config entry retires one
DAG and creates another rather than silently rewriting history. DAG code
changes don't version data — the ledger is what makes reprocessing safe
across versions.

## Failure modes this design addresses

- Upstream file late/absent → deferrable wait, SLA on the gate task, SLA-miss hook.
- Extract schema drift → contract validation fails before the gate, with a named cause.
- Bad data delivered → gate quarantines the file + writes a diagnosable report.
- Scheduler outage over a weekend → no catchup storm on recovery; explicit backfill if needed.
- Double delivery / retry mid-load → content-hash ledger no-ops or refuses loudly.
- Alerting outage → incident file still records; webhook failure never fails a task.

## Scaling notes

The demo warehouse is SQLite so everything runs anywhere; the load
semantics (ledger + upsert) are the portable part and map 1:1 to a
warehouse MERGE. Parse-time discipline matters at scale: the factory does
YAML + validation only at parse time (no external I/O), keeping scheduler
parse loops fast as feed count grows. `max_active_runs=1` per pipeline
prevents self-overlap; backfill parallelism is capped per-DAG so replays
can't starve daily runs.

## Verification

Executed locally and in CI: the full test suite (13 tests) — DagBag
integrity over all five DAGs (zero import errors, expected ids, tags +
retries hygiene, generated-graph shape, backfill trigger-only), plus unit
tests for the quality checks, the idempotent loader, config validation and
the backfill planner. The compose stack itself requires Docker and is the
documented path for a full runtime smoke test (webserver/scheduler/
triggerer); the DagBag tests are the parse-time guarantee CI enforces on
every change.

## What I learned / next steps

- TaskFlow reserves context names: a mapped argument called
  `logical_date` is rejected by `expand()` — found by the integrity tests
  doing exactly their job.
- Next: replace the SQLite warehouse with Postgres + a MERGE loader, add
  dataset-based lineage between the payments DAG and a downstream rollup
  DAG, and emit OpenLineage events from the gate operator.
